# Search Flow Implementation Plan

This plan follows [`docs/development/development_flow.md`](./development_flow.md) and the asynchronous boundary described in [`docs/search-high-level-architecture.md`](../search-high-level-architecture.md).

## Current Implementation Slice

The first implementation slice creates the type and mapping foundation, then registers route and service skeletons. It does not implement persistence, ONDC signing, network transport, callback correlation, or tests.

The application-level endpoints are:

```text
POST /logistics/search
GET  /logistics/search/:searchId/events
POST /on_search
```

`/logistics/search` is an internal BAP-facing request. `/on_search` is an incoming ONDC callback. SSE is an application-level stream and remains separate from ONDC wire payloads.

## Development Sequence

1. Define internal `SearchRequest`, response, normalized-result, and SSE event types.
2. Define ONDC `/search` and `/on_search` wire types using the exact snake_case fields from `ondc-docs.md`.
3. Add runtime validation for internal requests and incoming callbacks.
4. Create the internal-to-ONDC `/search` mapper.
5. Create the ONDC-to-internal `/on_search` normalization mapper.
6. Register the search, SSE, and callback routes.
7. Add controller and service seams for later persistence and outbound transport implementation.
8. Implement database persistence, signing, transport, callback correlation, SSE result publication, and search-window completion in later slices.

## Types

Internal types remain camelCase and are not reused as ONDC wire types. They cover:

- Search category and fulfillment type.
- Start/end locations and authorization.
- Provider schedule, ranges, and holidays.
- Shipment measurements, dimensions, declared value, and dangerous-goods status.
- Payment and collection amount.
- Pending search response and normalized provider results.
- `search_result`, `search_error`, and `search_completed` SSE events.

ONDC types cover the request context and intent, fulfillment locations, schedules, payload details, payment, provider catalog, categories, fulfillments, locations, items, static terms, and acknowledgement response.

## Mappers and Validation

The search mapper converts the internal request into the ONDC `/search` envelope and accepts protocol metadata such as transaction ID, message ID, timestamp, BAP ID, and BAP URI from the service layer. Internal IDs and SSE metadata are never sent to ONDC.

The `/on_search` mapper normalizes provider catalog data into application-facing results, including fulfillment distance tags and parent catalog-item references.

Runtime validation is separate from TypeScript types and rejects malformed search requests or callbacks before service execution.

## Route and Service Skeleton

`POST /logistics/search` validates the internal request and delegates to the search service. The intended completed behavior is `202 Accepted` with:

```json
{
  "searchId": "...",
  "transactionId": "...",
  "status": "pending"
}
```

The current service returns an explicit not-implemented response until persistence and ONDC transport are added.

`GET /logistics/search/:searchId/events` establishes an SSE stream through an in-memory manager. Multiple LSP results must eventually be published independently, followed by a completion event when the configured search window expires.

`POST /on_search` validates the callback and delegates to the callback service. The current callback service is a deliberate skeleton until transaction correlation, catalog persistence, and SSE publication are implemented.

## Asynchronous Boundaries

The system has two independent flows:

```text
BAP -> ONDC Network -> LSP -> /on_search -> BAP
BAP -> SSE -> frontend
```

The absence of a new `/on_search` response does not mean every LSP has responded. A named, configurable search window must control `search_completed` publication in the completed implementation.

The ONDC Registry is not the destination for `/search`; the BAP sends a signed request to the ONDC network/gateway.

## Deferred Work

- Drizzle transaction persistence for `ondc_transactions`, `logistics_searches`, and child records.
- ONDC signing and network transport configuration.
- `/on_search` transaction correlation and catalog persistence.
- Search timeout scheduling and durable search status.
- SSE result publication from callback processing.
- API and mapper tests, which are intentionally not part of this implementation slice.
