# Repository Instructions & Execution Policy (Codex)

These instructions define strict operational guidelines for this repository. They take precedence over standard defaults and must be applied strictly across all actions.

---

## 1. Git and Environment Files Policy (Read-Only Enforcement)

**NEVER stage, modify, remove, or commit anything to Git. NEVER write to or mutate any `.env`, secret, or configuration file.**
*This applies unconditionally, even if explicitly requested by the user during the turn.*

### Allowed Inspection Commands
- `git status`
- `git diff`
- `git log`
- `git show`
- `git blame`
- `git branch` (listing only)

### Prohibited Git Actions
- **Strictly Prohibited:** `git add`, `git rm`, `git commit`, `git push`, `git reset`, `git checkout`, `git restore`, `git stash`, `git merge`, `git rebase`, `git cherry-pick`, or any state-modifying Git command.
- **Protocol:** If the user requests a Git write operation, output the exact shell commands for the user to copy and execute manually. Do not invoke them via terminal execution tools.

### Environment & Secret File Rules
- **Reading:** `cat`, `grep`, or file inspection tools are permitted to read `.env` or credential files for debugging purposes.
- **Writing:** Do NOT write, edit, patch, or mutate `.env` files, `.env.*` variants, or secret files using string replacements, file writes, or shell redirections. Provide instructions for the user to make changes locally.

---

## 2. API Contract Enforcement

- Before modifying, implementing, or reviewing code that impacts API endpoints, schemas, or network data shapes, verify the relevant contract in `docs/integration-docs/`.
- If an API contract is ambiguous, missing, or contradictory, stop execution and request clarification from the user before writing code.
- Never infer or invent API contracts from contextual logic; the documented specification is the authoritative source.

---

## 3. Documentation Structure & Standards

Documentation is strictly maintained inside the `docs/` tree. Never create root-level markdown documentation or ad-hoc doc folders.

| Directory | Scope & Guidelines |
|---|---|
| `docs/integration-docs/` | **Frontend Integration:** Endpoints, request cURLs, response tables, SSE events, and user-facing error codes. *Excludes internal DB schemas, Redis keys, or backend class names.* |
| `docs/internal/` | **Backend Operations:** Database schemas, Redis key patterns (with TTL constants), service/repository architecture, and single-line changelog references. |
| `docs/deployment/` | **Infrastructure & Ops:** PM2/process topologies, deployment runbooks, and server configurations. |
| `docs/ARCHITECTURE_REVIEW.md` | **System State:** Single source of truth for open bugs, pending features, and integration tracking. |
| `docs/CHANGELOG.md` | **Historical Log:** Dated index of completed tasks and historical architectural updates. |

### Documentation Maintenance Rules
1. Every code change must update corresponding documentation in `docs/integration-docs/` (if API/frontend visible) and/or `docs/internal/` (if backend logic).
2. Before creating new documentation files, inspect the root directory and `docs/` subdirectories to prevent duplicate or orphaned files.
3. Include timestamps and concise descriptions for all doc changes. In `docs/internal/*`, reference entries in `docs/CHANGELOG.md` instead of restating historical narratives.

---

## 4. Definition of Done

A task is classified as complete only when all criteria are met:
1. Code implementation adheres to system standards and constraints.
2. API contract verification has been performed.
3. Required documentation updates under `docs/` are finalized.
4. User confirms build verification (for non-Python projects).
5. User explicitly validates functional behavior.

---

## 5. Architecture Review & Task Tracking (`docs/ARCHITECTURE_REVIEW.md`)

When operating in analysis, review, or planning modes:

- Record all findings and issue tracking directly in `docs/ARCHITECTURE_REVIEW.md`. Avoid adding ad-hoc inline TODO comments or external markdown notes.
- Tag every item with an explicit status: `[OPEN]`, `[CONFIRMED]`, `[DEFERRED]`, or `[WONTFIX]`.
- Do not execute code implementations for identified issues until the status is explicitly updated to `[CONFIRMED]`.
- **ONDC Wire Formats:** Network JSON formats, enum values, and field keys are frozen; never propose changes to these contracts.

### Resolving Tracked Items
When an item in `docs/ARCHITECTURE_REVIEW.md` is resolved:
1. **Remove** the item from `docs/ARCHITECTURE_REVIEW.md` (it must only list active/unresolved items).
2. Append **exactly one line** to the index table in `docs/CHANGELOG.md` using the format: `[Date] | [Tag] | [One-sentence description]`.

---

## 6. Technical & Architectural Rules

- **Source of Truth Hierarchy:** `ONDC Contract` $\rightarrow$ `PostgreSQL` $\rightarrow$ `Redis Cache` $\rightarrow$ `Frontend`. *(MongoDB is strictly audit-only and never authoritative).*
- **Redis Specifications:** Every new key pattern must define a named TTL constant, be documented in `docs/internal/<name>.md`, and include an explicit deletion site.
- **Database Schema Updates:** Requires a generated migration file, a documented before/after note in `docs/ARCHITECTURE_REVIEW.md`, and simultaneous updates across all affected repositories.
- **Performance Modifications:** Benchmark and document before/after query or operation metrics. Avoid non-quantifiable optimizations.

---

## 7. Changelog Override (`docs/CHANGELOG.md`)

- All persistent repository changes, technical decisions, and learnings must be appended to `docs/CHANGELOG.md`.
- `LEARNINGS.md` at the project root serves strictly as a lightweight pointer stub and must remain intact.
- Keep `docs/CHANGELOG.md` table entries strictly to a single line per item to maintain fast scannability.
